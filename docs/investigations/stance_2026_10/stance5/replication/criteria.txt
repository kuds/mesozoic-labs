RUN HANDLING (the maintainer's rules of 2026-10-22 16:32 UTC, run_log)
- Restart before the first checkpoint. A run cut off before its first periodic checkpoint (524,288) and restarted, as the Colab steps say, under "<RUN_ID>_b" (the same seed, branch and settings; the first folder is left alone and never judged) IS that run (Run 4 or Run 5). It is judged and scored under its RUN_ID. A further restart under "<RUN_ID>_c" likewise.
- Judge refusals. A judge that refuses on the run's own records (seed, commit, n_envs, hyperparameters, task, env kwargs, gate bars, plant, a missing stage_config.json) counts as an INVALID J file: the run does not hold. The refusal text is kept as a record, SP/foot/stance5/replication/judged/<RUN_ID>/refused_<steps>.json, and the scorer counts it as invalid. A refusal on the operator's side (a wrong path, a wrong clone, a missing local file) is fixed, and the checkpoint is judged again.
- Resumes. A resumed run (the same RUN_ID) is the same run, and its J checkpoints are judged as they stand. A file fetched before the resume and superseded by the resumed session's file of the same name is moved aside, never deleted. The judge file of a superseded checkpoint is moved aside too, and that slot is judged again.
- A cut-short final save. The run resumes from the newest intact periodic checkpoint in its own folder (the same RUN_ID). The final slot is only a stage1_final pair at 12,001,280 in that folder; without one, the final J file is missing.
- Ended. A run has ended when it finished at 12,001,280; or stopped early (gate_verdict.json written before 12,001,280: its stage1_final is not the final slot, so the final J file is invalid); or was lost past recovery or never started, and the maintainer declared it abandoned (recorded in the run log).
- Exists. The J checkpoints of a run are those in its Drive folder's 01_stance/models. --runs-ended is used once every one of them has been fetched, placed and judged, or its fetch has failed for good (A and B disagree and no tie-break copy matches; recorded in the run log).
- A scorer refusal (THE STANCE5 RUNS). The maintainer is told at once, and no line is read or acted on. Once the cause is found, the scorer is run again with every pinned file unchanged.
- No L4 for a resume. If no L4 is offered when a run is resumed, the maintainer tells the session that runs this package (the coordinator) before resuming on another runtime. The runtime is read and reported as in WHAT IS TRAINED, and never changes a verdict.

Nothing else enters the table. The K3 pass fraction against the control is reported, not a veto. stance5's rule (b) is not applied: under it adoption would be impossible, since the band arm already has two K3 failures, so its K3 fraction is at best 3/5, below the control's 2/3. stance5's (a) ("at least 2 of the 3 band runs HOLD") is replaced by line 1. Drift or split (D and S) is not read.
The menu is stance5 criteria decision line 4's three sub-items. In short (that text governs, with its evidence):
- for K1 on the actuator-saturation rail, the tail saturation habit;
- for K1 through other new failure modes (hop, nosedive, head contact), stance3 line 4's reading: the dose may be too strong;

Fails stay fails. Runs are never stopped or changed on their readouts, nor on a saturation alarm (D-D40 5a). A failed J checkpoint stays failed whatever later checkpoints read. Early reads at 1M and 2M are report-only.

WHEN THE DECISION IS READ
- The decision is read once both new runs have ended (RUN HANDLING, Ended). Until then, while a new run's J judge file is missing, the decision is "incomplete" and the scorer gives no line.
- Once the runs have ended and every J checkpoint that exists has been judged (RUN HANDLING, Exists), a J judge file still missing or invalid fails every criterion that needs it (score_stance5r.py --runs-ended), and the scorer lists those files.
- The decision is PROVISIONAL, and is not acted on, while any of these stands (the scorer prints each one):
  - a scorer pin is not filled: this file's sha256, judge_stance5r.py's sha256 or the HEAD;
  - this file's sha256 is not the pinned one;
  - the scorer runs with --validation, or with a HEAD other than cf80ecb14d1630ce3b4dcdea28a05835d143470b;
  - a new run's J judge file has a task_sha256 other than the band-on one, or a judge_sha256 other than judge_stance5r.py's pinned one;
  - before the runs have ended, a new run's J judge file is invalid;
  - with --runs-ended, a J checkpoint of a new run is placed under SP/foot/stance5/replication/runs (its 01_stance/models pair) without a judge file or a refusal record (an early stop's stage1_final is not a J checkpoint).
- The scorer REFUSES to score (no decision) when the stance5 runs' recorded verdicts do not reproduce (THE STANCE5 RUNS; then RUN HANDLING). It also refuses when frozen_params.json, the sidecar, score_stance5.py or score_stance3.py is not its pinned sha256, or when the sidecar's vector is not the recomputed mean.
- A decision that is neither incomplete, provisional nor refused is final.

KNOWN LIMITS
- n = 2 new seeds. Even if both hold, H = 3 of 5. The run-to-run variance is large: stance5 had 1 of 3 runs holding, and stance4's three control runs read 21, 30 and 0 of 40 clean at 6,291,456. Two more holds separate the recipe from seed luck only to that extent; this is inferred, and no significance level was set.
- GPU non-determinism. Colab GPU training is not bit-reproducible (inferred, as stance5 criteria state). A seed fixes the start, not the run, and a resume after a disconnect changes the trajectory. Matched seeds pair nothing across arms; per-seed comparisons are report only.
- The sigma rule is not a per-seed control. Seeds 42, 52 and 60 have their joint-noise sigma read from a control run of that seed (frozen_params.json "source": SP/foot/screen/runs/control_s<seed>/models/stage1_final.zip). Seeds 70 and 80 have no such run and use the mean of the three. Their K3 joint-space test is therefore not run under exactly the stance5 runs' conditions. The parent comparison's tie-break on noise falls mixes the two sigma sources.
- The reading rule was fixed after stance5's results were seen (2026-10-22 15:11 UTC), and before any training step of the new runs. So were the run-handling rules (16:32 UTC). Replicating on two more seeds was pre-registered in stance5's line 3; the "both must hold" rule was not.
- The new runs train a day after the stance5 runs and two days after the control, not side by side. The runtime type is the same. Colab's installed library versions are read from each run's records (MuJoCo 3.10.0 on the stance5 runs, from provenance.json), and a difference is reported, not a verdict change.
- The control is the stance4 runs as scored. The control's K3 fraction (2/3) rests on frozen per-seed sigmas, and the new runs' on the mean (above).

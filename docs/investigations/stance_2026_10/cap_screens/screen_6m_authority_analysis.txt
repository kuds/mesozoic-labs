11. CAVEATS
- One training run per seed; the 40 panel episodes of one policy are not replicates, and in-training evals are 10 deterministic episodes (fractions step by 0.1).
- The 6M lineage is a resume from stage1_3145728_steps: one PPO update short of an uninterrupted run (767 vs 768 updates), with RNG, environments and some callback state restarted at 3.15M. Not bit-identical to an uninterrupted 6M run.
- E2's projection is linear by rule; the s42 series is concave (quadratic t -4.3), so the linear 12M value likely overstates (inference). Its one-sided 95% interval (0.546-0.791) includes 0.60: a point-estimate failure, applied as predeclared.
- E4's binomial resolution is coarse: 37/40 vs 36/40 is one episode. s60 at 6M (36, two falls) is within one episode of the bar; s42 (30) and s52 (34) are not. E4 fails 0/3 regardless.
- The roll identification uses corner lift / tilt from the judge's per-episode window means; the judge does not record the roll component per foot, so which foot rolls and which way is not measured here.
- No control arm was run to 6M, so the 4-6M lateral failure rate has no same-budget control comparison; the comparison uses the 3M control (which fails CoP on almost every episode, so its roll failures are counted alongside).
- Linear extrapolations of tail_1 pitch (s52 0.9 at ~10M) are inference.
- run_arm.py's docstring stated lr_end 2.051424e-5 at launch while the code used 1.951424e-5 (per-update LR records confirm the latter); the docstring was corrected after launch (SHA256SUMS.at_launch vs SHA256SUMS).
- Nothing was committed, pushed or merged; the main checkout and the fix/screen2 worktree (94cab5ce, clean) were only read. This analysis only read run outputs and wrote under screen6m_auth/analysis_tools and screen6m_auth/analysis.{json,txt}.

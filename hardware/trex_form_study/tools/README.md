# Tools

Helpers for working on the form study, above all in a fresh cloud container. Run them from `hardware/trex_form_study`
unless stated. `LESSONS_LEARNED.md` §4 explains why each exists.

| Tool | What it does |
|---|---|
| `setup_venv.sh` | Builds the Python environment of `requirements-study.txt` (or another `REQS`) and checks the imports |
| `requirements-study.txt` | The versions the study's records name (Python 3.13.18) |
| `requirements-stage1-ppo.txt` | Stage 1's PPO environment: torch 2.9.0+cpu, stable-baselines3 2.9.0, gymnasium 1.3.0 |
| `restore_inputs.py` | Restores the git-ignored model files and arrays the records hash, checked by sha256 (below) |
| `keepalive.sh` | Heartbeat and watchdog runner that keeps a cloud session's container busy during long jobs |
| `watchdog_example.sh` | Template watchdog: starts every resumable chain that is neither done nor running |
| `memguard.sh` | Memory guard: side jobs are demoted and killed before protected training jobs when memory runs low |
| `lowprio.sh` | Runs a command at the lowest CPU priority, single-threaded |
| `report_page.py` | Turns a Markdown report into the owner's page (pandoc and `designlab/page_kit.py`) |
| `shot_page.js` | Screenshots a page as the Artifact publisher shows it and flags sideways overflow at phone width |

## A fresh container, in order

1. **System packages.**
   - Run `apt-get install -y libosmesa6`; without it the three rendering tests fail and no clip renders.
   - pandoc, ffmpeg, node and Playwright's Chromium come with the image.
   - The owner's cloud environment "mesozoic-labs" (made 14 Nov) does this step in its setup script, and step 2 as
     well.
2. **The venv.** `TORCH=cpu bash tools/setup_venv.sh` (1 min 43 s and 1.4 GB on 14 Nov, from the setup script).
3. **The keep-alive.** `mkdir -p logs && cp tools/keepalive.sh /tmp/keepalive_run.sh && sh /tmp/keepalive_run.sh
   logs/keepalive.log`, run with the Bash tool's `run_in_background` and `timeout` 7200000.
4. **The restore,** detached, so that no tool-call timeout stops it:
   `setsid nohup .venv/bin/python tools/restore_inputs.py restore > logs/restore.log 2>&1 < /dev/null &`
   (with `PYTHONPATH=.`).
   - It takes about 2.5 h on 2 processes (the times below).
   - Only a container restart stops it. Then run it again: files in place are kept. The look group, though, regenerates
     its 73 rungs in one scratch run, about 48 min, and starts that run over.
   - Do other work meanwhile: read the documents, ask the owner, test the Drive route.
5. **The check, then the suite** (commands below).
   - Compare with the fresh-worktree counts: 599 passed, 107 skipped, 0 failed.
   - With PR kuds/mesozoic-labs#668's branch merged, its 9 tests come on top.
   - If `check` reports a wrong sha256 after a restore, the container's CPU or BLAS may differ from the first
     session's. That one was an Intel Xeon @ 2.30 GHz, 4 CPUs, numpy's scipy-openblas 0.3.34 with the SkylakeX
     kernel. Stop and tell the owner; `copy-from` takes an unpacked archive of the files (below).

## restore_inputs.py: the git-ignored inputs of a fresh checkout

A fresh clone (a new container) has none of the study's git-ignored inputs: the round-two model files the Stage 1
plant reads, which every record key hashes (`round2/refine/<case>/models/<id>.{xml,json}`;
`designlab/stage1/panels.py` `key_context`), and the reference, transition and look-ladder arrays (`*.npz`). Without
the models the plant silently rebuilds them into `stage1/models/<body>/` with another model ledger JSON, so every record
key differs and `eval` and `sweep` refuse the checkout (`STAGE1_PLAN.md` decision 33, "Where it runs").
`tools/restore_inputs.py` puts back, byte for byte, every one of these inputs that the committed records pin, and says
what it cannot restore.

What it restores, in this order (models before arrays; the look ladder's Stage 0 price reads the picks' models; the
frozen reference sets come last, built on the picks' models and checked against the picks' and the ladder's arrays):

| group | files | sha256 listed in | regenerated by |
|---|---|---|---|
| `picks-models` | 6: `<id>.{xml,json}` of 60-N-T-10 and 60-N-H-10 in `round2/refine/narrow_carpet_60/models/`, of 75-M-H-10 in `round2/refine/feet_75/models/` | `stage1/runs/2026-11-08/stage1_inputs.json` (the XML's is the candidate record's `xml_sha256`, the ledger JSON's the one the eval records' keys hold) | one `pipeline.size_candidate` call per pick with the record's final overrides under the case's sizing settings, as arm K's helper sizes its own, with 2 BLAS threads (below) |
| `picks-arrays` | 84: `stage1/runs/2026-11-08/<pick>/refs/*.npz` and `transitions/*.npz` | the same list (as `refs.json` and `transitions.json` record them) | `refs.prepare`, then `transitions.prepare` from the restored references |
| `k` | 60: arm K's models and arrays | `stage1/runs/2026-11-10-speed/arm_k_inputs.json` | its helper: `arm_k_inputs.py models`, `arrays BODY refs`, `arrays BODY transitions` |
| `x` | 60: the -X bodies' models and arrays | `stage2/x/x_inputs.json` | its helper: `x_inputs.py models`, `arrays BODY refs`, `arrays BODY transitions` |
| `j` | 30: the Jetson body's models and arrays (2 model files, 10 references, 18 transitions of 75-M-H-10-J) | `stage2/j/j_inputs.json` | its helper: `j_inputs.py models`, `arrays BODY refs`, `arrays BODY transitions` |
| `look` | 73: `stage2/look/refs/<body>/<speed>/<variant>.npz` (about 50 MB) | `stage2/look/look_refs.json` | `python -m designlab.stage2.look prepare` into a scratch `--out` |
| `sets` | the arrays of every frozen Stage 2 reference set, `stage2/sets/<set>/<body>/{refs,look,transitions}/*.npz`: per frozen walk two files, per frozen move one (none while no set is frozen; a set that holds every item has 12 + 16 = 28) | the latest freeze in each `stage2/sets/<set>/<body>/set.json` (its manifest: `sha256`, a walk's `look_sha256`) | `python -m designlab.stage2.sets build --set S --body B`, in place: on a frozen set it writes no record and puts an array in place only when its sha256 is the manifest's |

Everything is regenerated in scratch directories (under `--scratch`, removed afterwards), and a file is put in place
only when its sha256 is the listed one; a right file is left alone, and no committed file is written (`restore` ends
with `git status`). At most `--procs` processes run at a time (default 2), at nice 10, with one BLAS thread each except
the picks' sizing (2 each, below). The one place `--procs` does not bound: arm K's and the -X helpers' `models` steps
size their two bodies at once whatever it is (each helper's own `Pool(len(jobs))`), so `--procs 1` still runs two
sizing processes there. `check` also compares each list with the committed records: the candidate records, the eval
records' keys, `refs.json` and `transitions.json`, for the look ladder `screen.json`, `metrics.json` and
`clips.json`, and for a frozen reference set the entries of its own `refs.json` and `transitions.json`. The `sets`
group is the one that is regenerated in place and not in a scratch directory: its builder holds the set's lock, works
in the set's git-ignored `partial/` directory and, on a frozen set, never writes a record.

A group is not run while a group it reads is not all here. `restore --group look` restores the picks' models first
when they are not all here; if they still are not (one CPU, below), it leaves the look ladder out rather than let the
ladder's clearance gate rebuild them into `stage1/models/<body>/` with another ledger JSON (`plant.model_files`), and
exits 1. `restore --group sets` likewise restores the picks' models and arrays first. A reference set on a body that
is no pick (the Jetson body, an expressive head) needs that body's own group; `sets build` refuses a body whose model
files are not here. Any file a run makes under `stage1/models` fails the run, which names it.

Run from `hardware/trex_form_study` with `PYTHONPATH=.`:

```
python tools/restore_inputs.py check [--group G ...]      # per group: matching / missing / wrong, and the list against
                                                         # the records; exit 0 only when all is here and agrees
python tools/restore_inputs.py restore [--group G ...] [--procs 2] [--scratch DIR]
python tools/restore_inputs.py copy-from DIR [--group G ...]   # from another checkout (its root or the study) or a
                                                         # directory holding the files at their study paths; each
                                                         # file checked by its sha256
python tools/restore_inputs.py not-restored              # what it cannot restore, and why
python tools/restore_inputs.py manifest [--from DIR]     # rewrite stage1_inputs.json from DIR's files (checked first)
```

Groups: `picks-models`, `picks-arrays`, `k`, `x`, `j`, `look`, `sets` (default: all; `restore --group look` restores
the picks' models first when they are not all here). The lists hold 6 + 84 + 60 + 60 + 30 + 73 = 313 files, and the
arrays of the frozen reference sets beside them.

Measured on 14 Nov 2026 in a fresh worktree of `4571826` (4 cores, `--procs 2`, nothing else running; the five groups
of that day, before `j` and `sets` were added on 15 Nov, which were not timed in a fresh worktree): `check` 0.6 s;
`restore` of everything 151 min (2 h 31 min): `picks-models` 5.0 min, `picks-arrays` 39.5 min, `k` 31.0 min, `x` 27.9
min, `look` 47.5 min, all 283 files with their listed sha256 and no tracked file changed; with one file of each group
overwritten, `restore` replaced the five in 7.5 min, and with one of each moved aside (after the review's fixes) it made
them again in 6.9 min, each byte for byte the moved file (the look rung's job takes 3 min, a pick's sizing 2 to 2.5);
`copy-from` of all 283 files from a checkout that has them 2.4 s. The full test suite then ran in that worktree, with
no `-q` (the repository's `pyproject.toml` already adds one, and a second hides pytest's counts line):

```
mkdir -p logs
MUJOCO_GL=disable PYTHONPATH=. python -m pytest -rs -p no:cacheprovider tests > logs/pytest.log 2>&1
echo PYTEST_EXIT=$? >> logs/pytest.log
```

pytest's own line: `599 passed, 107 skipped in 641.28s (0:10:41)`, then `PYTEST_EXIT=0`; the main checkout's last full
run (11 Nov) had 575 passed, 107 skipped, 0 failed, and the 24 more are this tool's (`tests/test_restore_inputs.py`).
The record-key tests (`tests/test_stage1_bodies.py`) recompute committed keys from the restored files. Of the 107
skips, 88 wait for an environment variable (73 `STAGE2_SLOW`, 15 `STAGE1_SLOW`); one wants the clips' media
(`LOOK_MEDIA`) and 18 policy-row tests want PPO checkpoints, neither of which this tool restores (with the checkpoints,
as in the main checkout, those 18 still skip outside the PPO venv, `train.PPO_VENV`).

The picks' models need more than one BLAS thread. The overnight refine run that sized them (8 Nov) set no thread limit,
so OpenBLAS took one per core, while arm K's and the -X runs set one, as their helpers do. The XML does not depend on
it, but with one thread each pick's ledger JSON differs from the recorded one in the last digit of a few dozen values
of its `evaluation` (the walks' inverse dynamics, whose double-support QP is thread-sensitive), and with it every record
key. With 2, 3 or 4 threads the ledger JSON is the recorded one, so the tool sizes with 2 (`SIZE_BLAS_THREADS`). A
process that may use one CPU only cannot reproduce it (OpenBLAS then runs one thread whatever it is told; `restore`
says so), and the look ladder then waits for the files too (above): under `taskset -c 0`, `restore --group look` with
60-N-T-10's model files and a rung missing made that pick's ledger JSON `236db045` against the recorded `b177e450`, put
neither file in place, left the look ladder out, made nothing in `stage1/models` and exited 1, in 2.4 min. Bring the
six files in instead: `copy-from DIR` takes another checkout, or any directory holding the files at their paths
relative to the study. With no other checkout in the container, pack them (about 3 MB) where they are, from
`hardware/trex_form_study`:

```
tar cf picks_models.tar round2/refine/narrow_carpet_60/models/60-N-T-10.xml \
    round2/refine/narrow_carpet_60/models/60-N-T-10.json round2/refine/narrow_carpet_60/models/60-N-H-10.xml \
    round2/refine/narrow_carpet_60/models/60-N-H-10.json round2/refine/feet_75/models/75-M-H-10.xml \
    round2/refine/feet_75/models/75-M-H-10.json
```

move the archive here (for example through the Google Drive connector's `create_file` and `download_file_content`, not
yet tried with a binary file), and unpack it into an empty directory: `mkdir -p DIR && tar xf picks_models.tar -C DIR
&& python tools/restore_inputs.py copy-from DIR --group picks-models` (14 Nov: a 2.96 MB archive, from which
`copy-from` put back 75-M-H-10's two files, byte for byte). The other way, running `eval` or `sweep` on the models the
plant rebuilds, takes `--allow-rebuilt-models`, and then every record key differs from the committed ones: the run
treats every committed record as stale, so give it a scratch `--out`.

Not restored (`not-restored` lists them with how many of their files the checkout holds):

- PPO checkpoints and VecNormalize statistics (`stage1/runs/*/<body>/{ppo,policy_only}/*/checkpoints/`): training
  outputs, regenerable only by retraining, and not bit for bit; the policy-row tests skip without them. The five
  judged checkpoints are committed (R3 on 75-M-H-10 at 2,506,752 steps, seeds 42 and 43; R4 on every body at 1,253,376
  steps), each model archive with its VecNormalize statistics, 10.6 MB in all. They are listed with their sha256 in
  `stage1/runs/2026-11-08/judged_checkpoints.json`, and every sha256 there is the one the policy rows' records hold.
  Load them in Stage 1's PPO venv (`tools/requirements-stage1-ppo.txt`), as the policy rows require.
- Eval traces (`stage1/runs/*/<body>/eval/traces/`, about 1.2 GB in the first session's checkout): each committed
  episode record holds its trace's path and sha256 (`panels.TRACE_RULE`), but all of them take the panels' core-hours
  again, and the R3 and R4 rows' also need the PPO checkpoints. A row's traces regenerate into a scratch run directory,
  the committed records left alone: `python -m designlab.stage1 eval --body B --rows ROWS --behaviors BEHAVIORS
  --inputs RUN --out SCRATCH`, with RUN the run directory that holds B's `refs` and `transitions`; compare each trace
  with its record's sha256. On 14 Nov seed 3042 of three Stage 1b turns came out byte for byte this way, with no
  tracked file changed: 60-N-T-10's R2@10ms `walking_0.35_left` and R2s/42@10ms `in_place_0.50_left`, and
  60-N-T-10-K's R2@10ms `walking_0.35_left`. Stage 2's G9 needs Stage 1b's 10 ms turn traces for toe clearance
  (`STAGE2_PLAN.md` section 4 B, item 3). Before G9, regenerate them as
  `stage1/runs/2026-11-10-speed/run_speed_round.sh` runs its rows, with `--behaviors turn` and a scratch `--out`, per
  body:

  ```
  python -m designlab.stage1 eval --body 60-N-T-10 --row-module designlab.stage1.speedfit --rows R2s/42@10ms,R2@10ms \
      --behaviors turn --workers 1 --inputs stage1/runs/2026-11-08 --out SCRATCH
  ```

  (the same for 60-N-H-10; for 60-N-T-10-K, `--inputs stage1/runs/2026-11-10-speed`, where its arrays are).
- The look clips' media (outside git; `stage2/look/clips.json` `media_dir`): `python -m designlab.stage2.clips render
  --media DIR --no-record` renders them again from the restored look arrays (not bit for bit: ffmpeg's encoder).
  Without `--no-record` the run also rewrites the committed `stage2/look/clips.json`.
- The round-one and round-two review MJCF and the sizing models no Stage 1 or Stage 2 body reads: `round1/review/mjcf`,
  `round2/review/mjcf`, `round2/review/mjcf/narrow_search`, `round2/refine/*/review/mjcf`,
  `round2/size_study/*/review/mjcf`, `round2/whatif_fr05/review/mjcf`, `round2/models`, `round2/refine/*/models` (the
  other refine cases', and the picks' cases' other files), `round2/refine/carpet_lift_models`,
  `round2/refine/fixed_models`, `round2/size_study/*/models`, `round2/whatif_fr05/models` and `round2/gait_tune/models`.
  The round-one and round-two commands regenerate them (`designlab.round1`, `round2`, `refine` with its `--carpet-lift`
  and `--fixed` passes, `sizestudy`, `whatif`, `gaittune`), and Stage 2 does not need them.

`not-restored` then lists any other git-ignored file in the checkout that no group lists and no item names (caches,
logs and the venv aside), so a new kind of output, or the plant's `stage1/models`, shows there.

## setup_venv.sh and requirements-study.txt

```bash
TORCH=cpu bash tools/setup_venv.sh            # venv at hardware/trex_form_study/.venv, CPU-only torch: 1.4 GB in all
```

```bash
REQS=tools/requirements-stage1-ppo.txt bash tools/setup_venv.sh /tmp/venv_ppo   # Stage 1's PPO set, in its own venv
```

On 14 Nov 2026 the CPU-only build took 50 s to 1 min 43 s in the cloud container and produced 1.4 GB; the default
build (torch from PyPI, with its CUDA libraries) is about 6 GB. A REQS other than requirements-study.txt is refused
for the default venv, so that it cannot replace the main environment's packages. The PyPI torch wheel brings
its CUDA libraries, which a CPU-only container does not use. The import check prints every version and the Stage 1
registry. Records since Stage 1 were made with the PyPI build of torch 2.15.0. The CPU-only build of the same version
passed `tests/test_stage1_ppo.py` (36 of 36, in 46 s), but the two builds have not been compared bit for bit on a
training run: record which one a run used.

## keepalive.sh

```bash
mkdir -p logs && cp tools/keepalive.sh /tmp/keepalive_run.sh && sh /tmp/keepalive_run.sh logs/keepalive.log [WATCHDOG...]
```

Run it with the Bash tool's `run_in_background` and `timeout` 7200000; the default timeout, 1800000, stops it after 30
min. Run a copy, because `sh` reads a script as it goes: editing `tools/keepalive.sh` during a run broke one on 14 Nov.

- **What it does.** It writes a line every 2 min (uptime, load, free memory) and runs the watchdog every 10 min, if one
  is given. It ends after 6,900 s, or as soon as `LOG.stop` exists.
- **While and after.** While it runs, the session tracks it and the container is less likely to be reclaimed as idle.
  When it ends, the session is re-invoked: re-arm it then.
- **Restarts.** A restart kills it, so check `uptime` and re-arm.
- **Settings.** Environment variables: `STEP=120`, `MAX=6900`, `EVERY=5` and `STOP_FILE`.
- **The watchdog.** `tools/watchdog_example.sh` is the Stage 1b speed round's watchdog, generalised. Copy it, set its
  chains, and pass it as WATCHDOG.

## memguard.sh and lowprio.sh

```bash
setsid nohup sh tools/memguard.sh logs/memguard.log >/dev/null 2>&1 &     # PROTECT="designlab.stage1 train" MIN_MB=1500
```

Every Python process whose command line lacks PROTECT gets `oom_score_adj` 800, each logged once. Below MIN_MB of free
memory, the largest of them gets SIGTERM. Set PROTECT to the Stage 2 trainers' command (for example the R5 entry
point's module name), or the guard kills them first.

```bash
bash tools/lowprio.sh python -m designlab.stage1 eval ...
```

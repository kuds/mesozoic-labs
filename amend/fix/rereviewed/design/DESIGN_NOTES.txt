2. THE COMPARATORS, AND WHAT A 3-AGAINST-3 DESIGN CAN AND CANNOT SAY
   2.1 What differs. STANCE6 and PC share the notebook, the seeds, the evaluation and checkpoint cadence, the
       stage config and every PPO setting. They differ in five ways:
       (a) the switch: the intervention.
       (b) HEAD's other bytes: the builder's commits. A6 requires the switch OFF to reproduce ROUND's V0 (h) rollout
           digests (ROUND l.780-793), so the code commit alone changes no training data on CPU.
       (c) GPU nondeterminism. A seed fixes the start, not the run. With A5 (a) the start is literally STANCE6's start:
           the same initial actor and critic functions and, on CPU, the same first rollout.
       (d) The date. The Colab image may have moved since 2026-10-27. The notebook pins mujoco, gymnasium and SB3
           (cell 3 at 8737cd3d). torch and numpy come from the image. STANCE6 recorded numpy 2.1.3; torch is not
           recorded [measured, F2 provenance.json.copy1 dependency_versions].
       (e) The K3 panel, only if CHOICE K3 turns it off. It was proven inert on CPU and inferred inert on GPU (ROUND
           l.674).
   2.2 STANCE6's measured outcomes [measured, DESIGN/comparators.out, which checks every ledger and probe copy against
       both the F2 fetch manifest and the run's artifact_manifest.json; classes from S2/r10round/f2/score.json]:
       s60: PARKED.
         - tail_3 MEAN_a +0.642; first tail_3 over-bar 8,126,464; CMD_L >= 0.60 in 37 of 91 evaluations, from
           6,946,816.
         - No alarm. GATE PASS. NEGATIVE.
         - TD 0.388227. Mean return 4412.6.
       s42: RAIL-LEDGER-PERSISTENT.
         - First over-bar 3,670,016. 22 TAIL ALARMs from 3,932,160. CMD_L >= 0.60 in 57 of 91.
         - GATE FAIL. NEGATIVE.
         - TD 0.635343. Mean return 4377.7.
       s80: CLEAR.
         - No tail over-bar. CMD_L >= 0.60 once, at 11,796,480 (+0.616).
         - 6 ANY ALARMs on neck_pitch_act (119 over-bar rows). GATE PASS. POSITIVE.
         - TD 0.154339. Mean return 4415.8.
       Each run has 1 fall in 910 evaluation rows. Under the PC reading's lines STANCE6 reads line 1 (r = 1).
   2.3 Per-run verdicts and report-only lines. With 3 runs per side, a verdict can only be per run, against a bar
       fixed before the runs:
       - TAIL CLASS, GATE CLASS, RUN OUTCOME and HABIT ELSEWHERE are such verdicts, and THE READING is built from
         their counts.
       - Comparisons between the arms are report only. That covers Statistic A, same-seed pairs, timing of first
         alarms, MEAN_a, returns and the critic readouts.
       - Binary outcomes cannot reach 0.05 against 3. With STANCE6 at 2 of 3 runs with a habit (RAIL or PARKED), 0 of
         3 PC runs gives one-sided Fisher p 0.20, and 1 of 3 gives 0.50. For RAIL alone (1 of 3) the best is 0.50
         [measured, comparators.out "Fisher" lines].
   2.4 The exact 3-vs-3 permutation test: used once, on one continuous statistic, as THE ONE TEST.
       - It splits the 6 values 3 + 3 in C(6,3) = 20 ways, so the smallest p is 1/20 = 0.05, reached only by complete
         separation [measured, comparators.out: the placements tried there give 1/20, 1/10, 3/10, 7/10 and 1].
         Only 1/20 depends on the placement alone (complete separation); for a sum statistic every other p
         depends on the magnitudes too: with the same placement [0.01, 0.02, 0.7] gives 6/20 and [0.1, 0.12, 0.9]
         gives 8/20 (fixer 2026-11-01, review I2 [measured, ST/review/fixer/scratch/i2_check.txt]).
       - Why use it at all. It is the only analysis in this design that can say "lower than every comparator" with an
         exact error rate under exchangeability. Fixing it now, on one statistic, blocks choosing among the many
         report-only measures after the data. That forking is the main risk of a 3-vs-3 historical design.
       - How. One-sided (PC lower), on the TD sum, with ties counted against H1, alpha 0.05.
       - What it means. The comparators' TDs are already known, so "p = 1/20" is the same as "every PC run's TD below
         0.154339". The text states the equivalence so nobody reads more into the p than a fixed bar.
       - What it never does. It does not decide a class, a per-run verdict or the line.
       - Missing runs. A run that is not COMPLETE and FINISHED enters at +infinity: missing never helps.
       - Exchangeability is assumed, not designed. The runs are not concurrent (2.1), and the caveat is printed with
         the result. [Superseded, section 9: the test now compares the PHASE runs with three concurrent switch-off
         runs (same HEAD, notebook, seeds, schedule); a missing PHASE run enters at +infinity, a missing OFF run at
         -infinity; STANCE6's values are printed beside, report only.]
       - The alternative is no test, with everything descriptive. That was rejected because without a pre-registered
         statistic the many readouts invite after-the-fact selection. The maintainer may still choose it (CHOICE TEST).
   2.5 Why TD, and the honest record of its choice.
       - TD is the mean over all evaluations of |CMD_L|. CMD_L is the 10-episode mean of the ledger's
         tail_3_pitch_act_command_mean, as BS2's SEC-CMD and read_bs.ledger_direct define it.
       - It is read only from eval_episodes.csv, a C3 file checked against the manifest. It needs no simulation and no
         new measuring code, so it is computed identically for STANCE6 (now, by comparators.py) and for PC (later, by
         the same code). The critic interface cannot touch it, because evaluation is actor-only, and VP0 asks the
         builder to show the evaluation callback writes the same rows with the switch ON and OFF.
       - It covers the whole run, so the time spent in a habit and its height both count. The absolute value counts a
         drive to the minus side too: s42's command swung to -0.56 between its spells [measured, comparators.out
         "min -0.5616 at 6946816"].
       - Before choosing, the designer computed two windows: all 91 evaluations, and from 4,194,304 (J's first). The
         comparators were in view. All 91 was chosen because it tunes nothing (no window is picked). The J window is
         printed beside it, report only (0.577658 / 0.808751 / 0.217914).
       - MEAN_a (M1 at R1/R2) was not chosen. It reads two checkpoints only and needs the adapted measuring copy, so it
         carries more adaptation risk.
       - The on-policy probe command was not chosen. policy_probe.npz is a readout file, not a C3 file.

3. WHAT THE CODE MUST GUARANTEE (A1-A7), AND WHY EACH IS A VALIDATION
   A1-A4 carry PS's verified contract (PS criteria.txt C1-C7, lines 154-204) over to a separate input. PS's version
   lived in the command slots. Here the phase must not touch the actor's 63 values at all. That is the maintainer's
   interface choice: valid for walking stages, whose commands use those slots.
   A5 (recommended (a)) makes the PC runs start where STANCE6 started. Initialising the policy exactly as 8737cd3d
   does (the same random draws), then appending zero phase columns to the critic's first layer, leaves the step-0
   networks as STANCE6's own functions. By main's widening precedent the actor is bitwise the same and the critic
   the same up to float32 round-off of the longer sum (|dV| <= 1e-6). So on CPU the first rollout's actor
   observations, actions, rewards and log-probabilities equal STANCE6's bitwise, compared field by field with
   rollbuf.py. The pinned whole-buffer digests include the values, so they match only if the build keeps V bitwise.
   Divergence then begins at the first update, which is the intervention.
   The alternative (b) is default initialisation of a wider critic. It would change every initial weight, and with
   it the actor's start, removing the one place the historical comparison can be exact.
   A6 shows the switch OFF is 8737cd3d. The comparators' configuration therefore exists on HEAD, and the only
   difference left is the switch.
   A7 keeps the deployed interface: plant_identity = ROUND's, observation_dim 63. The three config digests that do
   change must be pinned from a real stage_config.json, as ROUND's V0 (e) did, so that the launch check and C4 can
   compare them.
   VP0's list of tests is the builder's. The designer fixes only what they must show.
